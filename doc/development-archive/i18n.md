# Plan — UI Internationalization (i18n)

**Status:** Proposed
**Scope:** Server-rendered Thymeleaf UI only. Cookie-persisted locale, English fallback, no server-side persistence of the preference.
**Author context:** The app ships a browser-facing Thymeleaf UI (login, setup, dashboard, bots, integrations, usage, system-settings, event hooks) with every user-visible string hard-coded in English.

---

## Goal

Externalize all user-visible UI text into Spring/Thymeleaf message bundles, resolve the locale from a cookie (falling back to the browser's `Accept-Language`, then English), and expose language selectors on the login page and in a new **General application settings** section of `/system-settings`.

---

## Current state (traced)

- **Stack:** Spring Boot **4.0.5**, Java 21, `spring-boot-starter-thymeleaf` + `thymeleaf-extras-springsecurity6`. (Boot 4.0.5 ⇒ Thymeleaf 3.1 restricted-SpEL mode is ON — `T()`/`new` are forbidden in templates; the selector fragment below only uses `#locale`, which is unaffected.)
- **No i18n wiring exists:** `search_files` for `LocaleResolver`, `LocaleChangeInterceptor`, `WebMvcConfigurer`, `MessageSource` in `src/` returns **0** hits. `application.properties` has no `spring.messages.*` keys, so the default basename `messages` + UTF-8 encoding already apply — no config is strictly required, but explicit `spring.messages.basename`/`encoding` is worth pinning for clarity.
- **Partial groundwork already present (build on it, don't reinvent):**
  - `src/main/resources/messages_fr_test.properties` — a French **reference bundle** establishing the full key schema: `app.name`, `button.*`, `label.*` (incl. `label.generalSettings`, `label.language`), `locale.*` (native names for all 7 locales), `message.*`, `nav.*`, `page.*` (incl. `page.login.*`, `page.systemSettings.generalSettings*`). It is orphaned (no code/test references it) and has **duplicate keys** (`button.newIntegration`, `label.aiIntegration`, `label.gitIntegration`, `label.none`) plus some entries left in English. Treat it as the seed for `messages_fr.properties`, not as a finished artifact.
  - `src/main/resources/templates/fragments/locale-selector.html` — a ready-made Bootstrap dropdown fragment referencing `#{label.language}`, `${supportedLocales}`, `localeOption.code`, `localeOption.displayName`, and `#locale.toString()`. Not referenced by any template yet.
- **Login:** native mode is served by `SetupController.@GetMapping("/login")` → `"login"` view (OAuth mode has no login page and is out of scope for the selector). Login is `permitAll()` (formLogin).
- **System settings:** `SystemSettingsController.list()` → `"system-settings/list"`, a page of collapsible `<div class="card">` sections. A new "General application settings" card slots in cleanly at the top.
- **Global model:** `config/GlobalModelAttributes` (`@ControllerAdvice`) already exposes `appVersion`; it is the natural home for a `supportedLocales` attribute. **Test note:** `GlobalModelAttributesTest` constructs it with a single `ObjectProvider<BuildProperties>` arg — adding a constructor dependency breaks that test (and any `@WebMvcTest` slice that auto-detects the advice).
- **Templates:** 26 `.html` files under `templates/`, all with hard-coded English (labels, buttons, nav, section headings, empty-state text, inline `confirm(...)` strings, and the `data-tour-*` balloon-help tooltips in `layout.html`).
- **Test patterns:** `@WebMvcTest` (Boot 4 package `org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest`) + `@MockitoBean` (`org.springframework.test.context.bean.override.mockito.MockitoBean`), `spring-security-test`, flat (non-`@Nested`) test style.

## Target design

### 1. Message bundles

Create the English default/fallback plus the six translations as sibling files at `src/main/resources/`:

```
messages.properties        ← English (default AND fallback — canonical key inventory)
messages_fr.properties     ← seed from messages_fr_test.properties (dedup + finish untranslated entries)
messages_de.properties
messages_es.properties
messages_pt.properties
messages_ja.properties
messages_zh_CN.properties
```

- Key schema follows the existing French draft (`app.`, `button.`, `label.`, `locale.`, `message.`, `nav.`, `page.`). `messages.properties` is written first as the complete inventory; translations mirror it key-for-key.
- English fallback is automatic: `messages.properties` is the root `ResourceBundle`, so any missing key in a locale bundle resolves to English (satisfies AC "missing key → English").
- `messages_zh_CN.properties` — Spring's `StringUtils.parseLocale("zh_CN")` → `Locale("zh","CN")`, which resolves `messages_zh_CN.properties`. Files are UTF-8 (Boot's `MessageSourceAutoConfiguration` defaults encoding to UTF-8, so CJK text works as-is).
- `app.name` stays `AI Git Bot` in every locale (brand name, not translated).
- Delete/rename `messages_fr_test.properties` (its content becomes `messages_fr.properties`).

### 2. Locale resolution — resolver, interceptor, WebMvcConfigurer

New `config/I18nConfig` (`@Configuration`), no domain-package dependencies (safe under `ArchitectureTest`):

```java
@Configuration
public class I18nConfig {

    public static final String LOCALE_COOKIE = "lang";
    public static final String LOCALE_PARAM = "lang";

    public record LocaleOption(String code, String displayName) {}

    public static final List<LocaleOption> SUPPORTED = List.of(
            new LocaleOption("en",    "English"),
            new LocaleOption("fr",    "Français"),
            new LocaleOption("de",    "Deutsch"),
            new LocaleOption("es",    "Español"),
            new LocaleOption("pt",    "Português"),
            new LocaleOption("ja",    "日本語"),
            new LocaleOption("zh_CN", "简体中文"));

    @Bean
    public LocaleResolver localeResolver() {
        CookieLocaleResolver resolver = new CookieLocaleResolver(LOCALE_COOKIE);
        resolver.setDefaultLocale(Locale.ENGLISH);
        return resolver;
    }

    @Bean
    public LocaleChangeInterceptor localeChangeInterceptor() {
        LocaleChangeInterceptor interceptor = new LocaleChangeInterceptor();
        interceptor.setParamName(LOCALE_PARAM);   // ignoreInvalidLocale=true by default
        return interceptor;
    }

    @Bean
    public WebMvcConfigurer localeWebMvcConfigurer(LocaleChangeInterceptor interceptor) {
        return new WebMvcConfigurer() {
            @Override
            public void addInterceptors(InterceptorRegistry registry) {
                registry.addInterceptor(interceptor);
            }
        };
    }
}
```

Resolution precedence (all free, provided by `CookieLocaleResolver`):
1. Valid `lang` cookie → use it.
2. No/invalid cookie → `request.getLocale()` (`Accept-Language`).
3. Neither → `defaultLocale` = English.

"Unsupported browser language → English" is enforced two ways, no custom resolver needed:
- **Bundles:** a locale with no matching bundle (e.g. `it`, `ru`) renders every key from `messages.properties` (English) — the natural Spring fallback.
- **Manual selection:** `LocaleChangeInterceptor` defaults to `ignoreInvalidLocale=true`, so `?lang=xx` (unsupported) is dropped and the cookie is never set; browser/English fallback continues.

### 3. `supportedLocales` model attribute

Expose the list for the selector without adding a constructor dependency to `GlobalModelAttributes` (which would break `GlobalModelAttributesTest` and auto-detected `@WebMvcTest` slices):

```java
@ModelAttribute("supportedLocales")
public List<I18nConfig.LocaleOption> supportedLocales() {
    return I18nConfig.SUPPORTED;   // static single-source-of-truth, zero bean wiring
}
```

### 4. Locale selector (reuse the existing fragment)

`fragments/locale-selector.html` is used as-is. Each option links to the current page with `?lang=<code>`; `LocaleChangeInterceptor` sets the cookie *before* the controller renders, so the language changes on the same request (immediate, no extra redirect). Embed with the appropriate `baseUrl`:

```html
<!-- login page -->
<div th:replace="~{fragments/locale-selector :: localeSelector('/login')}"></div>

<!-- system-settings -->
<div th:replace="~{fragments/locale-selector :: localeSelector('/system-settings')}"></div>
```

### 8. Localize backend-provided UI strings (workflow catalog)

The three highest-value backend-originated texts are **user-visible** (rendered in the admin workflow UI), so they are *in* scope — unlike the "backend-only/internal identifiers" the issue excludes. They originate in Java and flow through the model, so they cannot use template `#{...}` keys directly; they need message keys resolved at the render boundary.

**Fields to localize** (traced from `WorkflowDescriptor` / `WorkflowParamField`):

| Field | Rendered at |
|---|---|
| `WorkflowDescriptor#displayName` | `workflows.html:65` (`row.displayName`), JSON endpoints `WorkflowConfigurationController:191` / `IssueWorkflowConfigurationController:185` (`out.put("displayName", ...)`) |
| `WorkflowDescriptor#description` | `workflows.html:71–73` (`row.workflow.description()`) |
| `WorkflowParamField#label` | `workflows.html:90` and `:114` |
| `WorkflowParamField#description` *(adjacent sibling — same form)* | `workflows.html:158–159` |
| `WorkflowParamField.EnumOption#label` / `#description` *(adjacent siblings)* | `workflows.html:152–154` |

`label` is user-visible and cannot be localized alone while its sibling `description` and the enum-option labels in the *same* rendered form stay English — so all five are localized together.

**Non-visual consumers that must not regress** (a raw key would leak here):
- `PrWorkflowRegistry:50` / `IssueWorkflowRegistry:49` — startup log "registered <displayName>" (dev-facing; resolve with English or tolerate the key).
- `WorkflowSelectionService.saveSelection():143` — `"Workflow '<displayName>': <validation error>"`, surfaced to the admin as a flash error. Resolve before emitting.

**Scope covers both SPIs:** `PrWorkflow` *and* `IssueWorkflow` both extend `WorkflowDescriptor`, so this touches the issue workflows too. Current hardcoded call sites: `ReviewWorkflow`, `AgentReviewWorkflow`, `UnitTestWorkflow`, `ReadmeSyncWorkflow`, `I18nCoverageWorkflow`, `TriageIssueWorkflow`, `CodingIssueWorkflow`, `WriterIssueWorkflow`.

**Approach (ADR-2 below):** descriptors carry dotted message keys (`workflow.<key>.name`, `workflow.<key>.description`, `workflow.<key>.param.<name>.label` / `.description`, `workflow.<key>.param.<name>.enum.<option>.label` / `.description`), resolved to text via an injected `MessageSource` at the UI boundary. English fallback is the `messages.properties` root bundle, unchanged.

Concrete changes:
- [ ] Change `displayName()` / `description()` / `paramsSchema()` labels in the 8 workflows above to return dotted keys; add the keys to `messages.properties` + the 6 translations.
- [ ] NEW `WorkflowTextResolver` (e.g. in `prworkflow.config`) — `MessageSource`-backed helpers: `displayName(WorkflowDescriptor)`, `description(WorkflowDescriptor)`, and `List<WorkflowParamField> localizedFields(WorkflowParamsSchema)` (returns copies with resolved label/description/enum labels; validation keeps using the originals).
- [ ] Resolve `displayName` in `WorkflowSelectionService.loadAvailableWorkflows()` (row build) and the `saveSelection()` error path; the JSON endpoints reuse the already-resolved row.
- [ ] Localize the param fields before render in `workflows.html` — resolve in `WorkflowConfigurationController` / `IssueWorkflowConfigurationController` (map the schema through the resolver into the model) so the bot Details modal (fed by `describeParams`/`describeSelections`) gets the same text from one helper. (Thymeleaf dynamic keys `#{__${field.label}__}` are a fallback but do NOT cover the JSON/modal paths.)
- [ ] Leave `WorkflowParamsValidator` untouched — it reads `name`/`type`/`required`/`allowedValues.key`, never the display strings.

**Out of scope (separate follow-ups unless requested):** MCP tool descriptions and `AiProviderMetadata.getDisplayName()` — different families that also reach LLM prompts, so localizing them needs a separate decision about whether *prompts* should be localized at all.

### 9. Localize ToolCatalog tool descriptions (split UI-facing vs LLM-facing)

`ToolCatalog` is the single source of truth for built-in tool descriptions, all hardcoded English: `STATIC_TOOLS` (`Entry.description()`, ~25 built-in tools) and `VALIDATION_DESCRIPTIONS` (9 validation tools). The **same** description string serves two consumers:

1. **LLM native descriptors** — `ToolCatalog.nativeDescriptors()` → `ToolDescriptor(name, description, schema)` → the AI provider's function-calling API. Not user-visible; it governs what the model is told about each tool.
2. **Admin UI** — `BuiltinToolRegistry.builtinTools()` → `toolCatalog.describeFor(role, name)` → `BotToolSelectionService.loadAvailableTools()` → `BotToolSelectionRow.description` → serialized into `bot-tools-selection.html` via `th:inline="javascript"` (`const allTools = /*[[${tools}]]*/`), rendered at line 263. Also `BotController.selectedBuiltinTools()` JSON (bot Details modal).

**Decision (ADR-3 below):** localize **only the UI-facing description**; keep the LLM native descriptor English.

- **Tool names** (`write-file`, `rg`, `cat`, …) are stable identifiers persisted in `bot_tool_selections.tool_key` and passed to the model as function names — never translated.
- **UI descriptions** are a separate, operator-facing string — independent of the LLM description, *not* a translation of it (an operator reads "Whitelist a directory", the model reads "Create a directory and any missing parents"). They come from message keys `tool.<name>.description` resolved via `MessageSource`; English `messages.properties` is the fallback, so a tool without a `tool.*` key keeps its existing English text.
- **LLM native descriptions** (`Entry.description()` + `VALIDATION_DESCRIPTIONS`) and the **JSON-schema property descriptions** (`prop("path","string","...")`) stay English — the model's system prompts and every `PromptLibrary` are English, and translating the tool schema would degrade agent reliability. That is a separate, riskier decision.

Concrete changes:
- [ ] Inject `MessageSource` into `BuiltinToolRegistry`; when building `BuiltinTool.description`, resolve `tool.<name>.description` with fallback to `toolCatalog.describeFor(...)` (the current English text). Resolution happens in Java, so the `th:inline="javascript"` serialization and the bot Details modal JSON both receive localized text automatically.
- [ ] Add `tool.<name>.description` keys for all ~25 built-in + 9 validation tools to `messages.properties` (English values = current strings) + the 6 translations.
- [ ] Leave `ToolCatalog.STATIC_TOOLS`, `VALIDATION_DESCRIPTIONS`, `nativeDescriptors()`, and the schema `prop(...)` descriptions untouched (LLM-facing English).

Adjacent items (separate, unless requested):
- Tool **kind** labels currently render as raw enum names in `bot-tools-selection.html` (`tool.toolKind` → `FILE`/`CONTEXT`/`VALIDATION`/`REPOSITORY`, lines 131/221/252). Localizing them is a small follow-up (`toolKind.*` keys + a display mapping), independent of the description work.
- Schema property descriptions are LLM-only and deliberately stay English.

## Risks / watch-list

- **Thymeleaf 3.1 restricted SpEL:** `messages_*.properties` keys with `T()`/`new` are forbidden — the selector fragment avoids them; do not introduce `T(Locale).X` in any template.
- **CJK encoding:** `.properties` must be UTF-8 (default in Boot 4) — do not switch `spring.messages.encoding` to a legacy charset.
- **`zh_CN` locale shape:** cookie value must be exactly `zh_CN` (not `zh-Hans`) to match both the bundle filename and the fragment's `#locale.toString()` active-check.
- **Don't localize data:** entity names, workflow/bot/integration names, dates, and generated content stay as-is — only UI chrome and static application text get keys.
- **Don't persist the preference server-side:** out of scope — no DB column, no `AdminUser` field, no `SystemSettings` table change.
- **Raw-key leakage in workflow strings:** once `displayName()`/`description()`/`label` carry keys, `PrWorkflowRegistry`/`IssueWorkflowRegistry` startup logs and the `saveSelection()` validation flash will show raw keys unless resolved first — resolve the display name at both sites (English fallback).
- **Don't break param validation:** `WorkflowParamsValidator` reads `name`/`type`/`required`/`allowedValues.key` only; the keyized `label`/`description` must stay transparent to it (resolve at the render boundary, never in the schema itself).
- **Keep LLM tool schemas English:** ToolCatalog descriptions feed BOTH the admin UI and the LLM's native function-calling descriptors. Localize only the UI copy (`BuiltinToolRegistry` + `tool.*` keys); `nativeDescriptors()` / `VALIDATION_DESCRIPTIONS` / schema `prop(...)` must stay English so agent behavior is unchanged.
- **OAuth mode:** there is no login page in OAuth mode; the `/system-settings` selector still works, so OAuth deployments still get manual language switching (the login-page selector simply isn't rendered there).

## ADR-1: Locale resolution mechanism

**Status:** Proposed

**Context**
The UI must resolve language from (a) an explicit user selection persisted client-side, (b) the browser's `Accept-Language` on first visit, and (c) English as a final fallback — with no server-side persistence. Spring offers several resolver strategies; the choice affects both the resolution precedence and how "unsupported locale" is handled.

**Options Considered**
1. **`CookieLocaleResolver` + `LocaleChangeInterceptor` (standard Spring approach)**
   - ✅ Pros: cookie precedence > `Accept-Language` > default is the built-in behavior; `LocaleChangeInterceptor` gives the `?lang=` switching for free and ignores invalid locales by default; zero custom code; matches the issue's "standard Spring + Thymeleaf" instruction.
   - ❌ Cons: "supported locales" is not an explicit whitelist — an unsupported cookie value must be rejected (interceptor handles the `?lang=` path; bundle fallback handles the render path).
2. **`SessionLocaleResolver`**
   - ✅ Pros: same interceptor story.
   - ❌ Cons: server-side session state, not a cookie; violates the "client-side cookie only" requirement.
3. **Custom `LocaleResolver` with an explicit supported-locale whitelist**
   - ✅ Pros: hard guarantee that only the 7 locales are ever active.
   - ❌ Cons: more bespoke code for behavior the bundle fallback already provides; diverges from the "standard approach" the issue asks for.

**Decision**
Option 1 — `CookieLocaleResolver` (cookie `lang`, default `Locale.ENGLISH`) with a `LocaleChangeInterceptor` (param `lang`) registered via a `WebMvcConfigurer`. "Supported" is enforced by which bundles ship (7 locales + English root) and by the interceptor's `ignoreInvalidLocale=true`, so an unsupported language renders English with no extra code.

**Consequences**
- The preference lives only in the browser cookie; server holds no state (AC-6).
- Any page can switch language by linking `?lang=<code>`; the two selectors reuse one fragment.
- Adding a language later = add one `.properties` file + one `SUPPORTED` entry (and the same `locale.*` display name in each bundle).
- Fallback is two-layer (bundle root + default locale), so partial translations degrade gracefully to English.

## ADR-2: Localizing backend-provided workflow strings

**Status:** Proposed

**Context**
`WorkflowDescriptor.displayName()` / `description()` and `WorkflowParamField.label` (plus its `description` and `EnumOption` labels) are hardcoded English in workflow classes but rendered in the admin workflow UI (`workflows.html`, the JSON endpoints, the bot Details modal). They must follow the same English-fallback i18n as the templates, but they arrive via the model rather than template literals, so `#{...}` does not apply directly.

**Options Considered**
1. **Descriptors carry message keys; resolve via `MessageSource` at the render boundary**
   - ✅ Pros: consistent dotted-key schema with the rest of the bundles; one resolver helper covers `workflows.html`, the JSON endpoints and the bot Details modal; validation untouched; English fallback is free.
   - ❌ Cons: Java signatures change (`displayName()`/`description()`/`label` now carry keys); the two non-visual consumers (registry logs, validation error) must resolve or tolerate keys.
2. **English literal as the message key (code-as-message + `useCodeAsDefaultMessage`)**
   - ✅ Pros: no Java changes; the literal doubles as the fallback.
   - ❌ Cons: long sentences as keys are fragile (any whitespace/punctuation drift breaks the lookup); inconsistent with the dotted-key convention already established in `messages_fr_test.properties`.
3. **Resolve keys inline in Thymeleaf via `#{__${...}__}` preprocessing**
   - ✅ Pros: no Java resolver class.
   - ❌ Cons: couples the template to message-key resolution; does not cover the JSON endpoints or the bot Details modal (which bypass Thymeleaf); harder to unit-test.

**Decision**
Option 1 — descriptors return dotted keys under `workflow.*`; a single `WorkflowTextResolver` (backed by the auto-configured `MessageSource`) resolves them at the UI boundary. The two non-visual consumers resolve the display name (English fallback) before emitting.

**Consequences**
- `displayName()` / `description()` / `label` / `description` / `EnumOption` labels become dotted keys; all 7 bundles gain the `workflow.*` section.
- Templates, JSON endpoints and the bot Details modal stay dumb — they receive resolved text, not keys.
- `WorkflowParamsValidator` is unaffected (it never reads the display strings), so persisted params and validation semantics do not change.
- The 8 concrete workflow implementations are the only files whose display strings change; the resolver centralizes the `MessageSource` lookup.

## ADR-3: Split tool descriptions into UI-facing (localized) vs LLM-facing (English)

**Status:** Proposed

**Context**
`ToolCatalog`'s per-tool `description` is hardcoded English and serves two masters: the admin UI (bot tool-selection editor + bot Details modal) and the LLM (native function-calling descriptors). Localizing it wholesale would change the text the model receives — while the model's system prompts and every `PromptLibrary` remain English.

**Options Considered**
1. **Localize both surfaces (UI + LLM)**
   - ✅ Pros: one description string, simplest code.
   - ❌ Cons: the model gets non-English tool schemas while the rest of its context is English — inconsistent and likely degrades agent reliability; adds translation maintenance for machine-only text.
2. **Split — localized UI description (message key) + English LLM native description (unchanged)**
   - ✅ Pros: operators see localized, human-facing text; the model keeps English tool schemas (byte-identical); English fallback (`messages.properties`) means untranslated tools are unaffected; zero behavior change for the agent.
   - ❌ Cons: two description sources per tool to maintain (intentionally independent — operator-facing vs model-facing, wording may diverge); a new `tool.*` key family to maintain.
3. **Keep tool descriptions English everywhere**
   - ✅ Pros: zero risk.
   - ❌ Cons: leaves visible English in the admin UI — fails the i18n acceptance for a user-visible surface.

**Decision**
Option 2 — split. UI descriptions resolve from `tool.<name>.description` via `MessageSource` at the `BuiltinToolRegistry` boundary (English fallback = current text); the LLM native descriptors and schema property descriptions stay English.

**Consequences**
- Agent behavior is unchanged (native descriptors byte-identical to today).
- Tool names remain identifiers; only descriptions are translated.
- English is the fallback, so a tool without a translation still shows its current description.
- The `tool.*` key family is additive; `STATIC_TOOLS` / `VALIDATION_DESCRIPTIONS` remain the LLM-facing source.
- The UI and LLM descriptions are fully decoupled: the UI copy can be rewritten for operators (shorter, friendlier) independently of the LLM copy, which stays byte-identical to today. The data sent to the LLM is not involved in i18n at all.
